# The dev IRC server

A real IRC server on loopback, so the connection path can be exercised without
unfiltered egress or a public network's goodwill. It is [ergo](https://ergo.chat),
not a mock: real TLS, real registration, real `ISUPPORT`, real server-side
state.

Everything it generates lands in `dev/ergo/`, which is gitignored and entirely
disposable.

## Start and stop

```bash
make dev-server        # up, and wait until the TLS port actually accepts
make dev-server-logs   # follow it
make dev-server-stop   # stop, keeping accounts and certificates
make dev-server-clean  # stop and throw all of dev/ergo/ away
```

`--wait` blocks on the healthcheck, so a test can run the moment
`make dev-server` returns.

## What is on it

| | |
|---|---|
| **Connect to** | `localhost:6697` or `127.0.0.1:6697` — **TLS only**, loopback only |
| Network name | `ErgoTest` — what it calls its network |
| Server name | `ergo.test` — what it calls *itself*. See below |
| Certificate | `dev/ergo/fullchain.pem`, self-signed, valid one year |
| Names on the certificate | `localhost`, `127.0.0.1`, `::1`, `ergo.test` |

> **`ergo.test` is not an address.** It is the name the server announces for
> itself, and it appears on the certificate, but nothing resolves it — `.test`
> is a reserved TLD with no DNS records anywhere. Connecting to it fails with a
> DNS error. The same goes for `ircd`, the Compose service name: that only
> resolves *inside* the Docker network, not from your machine. Use `localhost`
> or `127.0.0.1`.

There is no plaintext port. `ddirc-core` sets `use_tls: true` unconditionally,
so a plaintext dev server would be unreachable from the very code it exists to
test.

The certificate is regenerated by `make dev-server-clean`. Anything that
trusted the old one is then trusting a key that no longer serves anything.

## Connecting to it

### From the Rust tests — the supported path

```bash
make dev-server
make test-integration
```

`irc-core/ddirc-core/tests/dev_server.rs` points `extra_root_cert` at
`dev/ergo/fullchain.pem`, which **adds** a trusted root for that one
connection. It does not disable verification, and one of the tests in that file
asserts that without it the same connection is refused — so if verification is
ever weakened, the suite says so instead of quietly proving nothing.

Override the path if your checkout is somewhere unusual:

```bash
DDIRC_DEV_CERT=/path/to/fullchain.pem make test-integration
```

### By hand, to see it answer

```bash
printf 'NICK probe\r\nUSER probe 0 * :probe\r\nQUIT :bye\r\n' \
  | openssl s_client -connect 127.0.0.1:6697 \
      -servername localhost -CAfile dev/ergo/fullchain.pem -quiet
```

You should get `001 probe :Welcome to the ErgoTest IRC Network` and a couple of
`005` lines. If that works, the server is fine and anything else that fails is
a client-side trust problem.

### Registering an account, for SASL

Ergo accepts `REGISTER` before you are connected, which is what makes SASL
testable at all — there is no chicken-and-egg with an account you cannot make.

```
REGISTER <account> <email|*> <password>
```

`*` skips e-mail verification, which is enabled on this server. So, in the
`openssl s_client` session above:

```
REGISTER myaccount * mypassword
```

The reply is `REGISTER SUCCESS <account>` followed by numeric `900`, logging
you straight in. Passwords have a minimum length; short ones come back as
`FAIL REGISTER`.

### From ddIRC itself

**It will not connect out of the box, and that is deliberate.**

The client verifies certificates and has no "trust this one" setting. The
`extra_root_cert` field exists only on the core's `ServerConfig`; the FFI
layer's own `ServerConfig` has no such field, so nothing the app can configure
ever reaches it. A self-signed server is refused, which is the whole point —
a "just skip verification for testing" switch would be a
verification-skipping path sitting in the shipped client.

Three ways round it, cheapest first.

**1. Test the UI against a real network.** For looking at the interface —
unread badges, the connecting pulse, the channel list, mIRC colours — any
public network works and needs no changes at all:

```
irc.libera.chat:6697
```

It costs nothing and touches no trust settings. If you are testing the
*interface* rather than the connection, stop here.

**2. Launch the app with `SSL_CERT_FILE` pointing at the certificate.** This is
the one to use for the dev server. `rustls-native-certs` reads that variable in
place of the platform's store, so the trust change lives and dies with the
process — nothing is installed, and a normal launch is unaffected.

```powershell
$env:SSL_CERT_FILE = "$PWD\dev\ergo\fullchain.pem"
.\build\windows\x64\runner\Debug\ddirc.exe
```

```bash
SSL_CERT_FILE="$PWD/dev/ergo/fullchain.pem" \
  ./build/windows/x64/runner/Debug/ddirc.exe
```

Then add a network with address `localhost` and port `6697` — **address only,
no port in that box**; the port has its own field.

Verification stays fully on: the app checks the certificate against the file
you named and the hostname against its SAN. It is not a skip, it is a
different, smaller list of roots. Note the flip side — while the variable is
set the app trusts *only* that certificate, so a public network will not
connect in the same run.

**3. Trust the certificate on this machine.** The core builds its trust store
from `webpki-roots` plus the platform's own store, so once Windows trusts this
certificate, ddIRC connects to `localhost:6697` with verification fully on.
Nothing in the client is weakened; the operating system simply now agrees that
this certificate is genuine.

```powershell
# Import (Windows may show a security warning you have to accept)
Import-Certificate -FilePath dev\ergo\fullchain.pem `
                   -CertStoreLocation Cert:\CurrentUser\Root

# Check it landed — subject is O=Ergo
Get-ChildItem Cert:\CurrentUser\Root | Where-Object { $_.Subject -eq 'O=Ergo' }

# Remove it again when you are done
Get-ChildItem Cert:\CurrentUser\Root |
  Where-Object { $_.Subject -eq 'O=Ergo' } | Remove-Item
```

Then add a network in ddIRC pointing at host `localhost`, port `6697`.

Prefer option 2 unless you need the app to reach the dev server and a public
network in the same run. Read this part before you run it:

- The matching **private key sits next to the certificate** in
  `dev/ergo/privkey.pem`. Anyone who gets that file can impersonate
  `localhost`, `127.0.0.1` and `ergo.test` to you for as long as the
  certificate is trusted. That is a narrow blast radius, but it is not zero.
- `CurrentUser`, never `LocalMachine`. Do not do this on a shared machine.
- `make dev-server-clean` generates a **new** pair. The old root stays trusted
  and stops matching anything. Remove it with the command above.
- The certificate in this checkout is
  `B8:A5:1F:63:78:FA:8C:9A:98:87:74:16:E6:17:21:EB:10:B2:F3:F9` (SHA-1) and
  expires a year after it was generated. Yours will differ.

### From another IRC client

Point it at `localhost` port `6697` with TLS on, then either hand it
`dev/ergo/fullchain.pem` as a trusted CA file (HexChat, irssi and WeeChat all
take one) or use its own accept-invalid-certificate option. No account is
needed unless you are testing SASL.

## When it will not connect

**A DNS error / "no such host"** — you are almost certainly using the wrong
name. The only things that resolve are `localhost` and `127.0.0.1`. Neither
`ergo.test` (a reserved TLD with no DNS records) nor `ircd` (the Compose
service name, which only exists inside the Docker network) will resolve from
your machine.

Check for yourself, from a shell:

```bash
nslookup localhost    # answers
nslookup ergo.test    # Non-existent domain
```

If you would rather connect as `ergo.test` — the certificate does cover it —
add `127.0.0.1 ergo.test` to `C:\Windows\System32\drivers\etc\hosts`, as
Administrator. Nothing here requires it.

**A certificate error** — expected, and covered under *From ddIRC itself*
above. The client will not accept a self-signed certificate.

## When it will not start

**`docker info` fails / `npipe:////./pipe/dockerDesktopLinuxEngine` not found**
— Docker Desktop is not running. Start it and wait for the whale to settle
before `make dev-server`.

**Port 6697 already bound** — something else is on it, most likely a previous
container. `docker ps` and then `make dev-server-stop`.

**`no dev server certificate at ...`** from the tests — the server has never
been started in this checkout, so nothing has generated a certificate yet. Run
`make dev-server` first.

**The server starts but nothing connects** — check the certificate has not
expired (`openssl x509 -in dev/ergo/fullchain.pem -noout -dates`). If it has,
`make dev-server-clean` and start again.
